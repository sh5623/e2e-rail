# e2e-rail 통합 게이트 비용 개선 보고서

작성일: 2026-10-14 KST · 작성: Codex · 수신: Claude 교차검증 및 후속 구현 담당

기준: e2e-rail `0.3.3`, 로컬 HEAD `4ca1a82` (0.3.3 릴리스 이후 검증 문서·락 테스트 수정 포함). 상태: **구현 제안 및 검증 계약 초안**. 명령·모듈·데이터 필드의 신규 이름은 모두 제안이며 현재 CLI에서 실행할 수 있다는 뜻이 아니다.

## 1 목적과 우선순위

각 작업이 게이트를 통과한 뒤 동료의 변경을 에픽에 합치면서 긴 게이트를 반복하는 비용을 줄인다. 작업의 줄 수나 단순함 대신, **실제로 검사한 입력·통합으로 바뀐 입력·아직 증거가 없는 영역**을 기준으로 판단한다. 복잡한 작업도 독립적일 수 있고, 한 줄의 공용 상태 변경은 넓은 재검증이 필요할 수 있다.

권장 순서는 **측정 → 동일 실행 중복 제거와 통합 후보 고정 → 동일 입력 증거 재사용 → 통합 영향 분석과 테스트별 재사용 → 프로젝트 전체 게이트 연동**이다. 처음부터 AI에게 게이트 생략 권한을 주지 않는다. 기계가 재사용 후보를 계산하고, AI는 숨은 결합을 찾아 검사 범위를 확대한다.

이번 요청의 산출물은 이 보고서다. 후속 구현자는 Claude의 교차검증 판정과 구현 착수 요청의 범위에 따라 작업한다. 이 문서는 BFM의 게이트 규약 변경, 에픽 자동 푸시 권한, 저장소 보호 규칙 변경, 릴리스·설치를 승인하지 않는다. 이미 주어진 사용자 권한은 중복 확인하지 않는다.

## 2 확인한 현행 구조와 병목

| 근거 | 현재 동작 | 개선할 지점 |
| --- | --- | --- |
| `src/fingerprint.mjs`의 `computeFingerprint` | HEAD·미커밋 diff·untracked·설정·Playwright 버전·preview dist를 지문에 반영 | 내용이 같아도 HEAD 변경으로 실행 증거가 오래된 것으로 판정될 수 있음 |
| `src/verify.mjs`의 `verify` | 앱·mode·지문·검증 정책이 맞는 full 또는 완전한 shard 묶음을 인정. selected는 별도 요구 조건 | 다른 지문에서 얻은 증거를 연결하는 통합 검증은 없음 |
| `src/ledger.mjs` | 실행별 append-only JSONL, `VERIFY_POLICY = 2`, clean full 기반 last-green | 실행 이력과 재사용 판정을 분리한 증거 구조 필요 |
| `src/run.mjs` | 머신 락 → 필요시 build → 지문 계산 → 실행 → 원장 | 같은 요청이 대기 중·실행 중일 때 결과를 공유하는 기능 필요 |
| `src/lock.mjs` | 머신별 heavy 배타·light 슬롯, FIFO 요청 순서 | 부하 락은 에픽 통합 순서나 Git 쓰기 소유권을 관리하지 않음 |
| `src/select.mjs`, `src/graph.mjs` | 변경 → 그래프·라우트·API 영향, 미해석 시 확대 | 두 변경 사이 상호작용, 테스트별 입력 동일성은 별도 설계 필요 |
| `src/run.mjs`의 `parsePlaywrightReport` | spec×project 집계, 일부 테스트 skipped여도 나머지가 통과하면 행은 passed 가능 | 엄격한 재사용에는 테스트별 실행 목록·결과가 필요 |
| `skills/measure/SKILL.md` | 느린 spec·retry·worker·shard 측정 | 전체 게이트의 큐·유닛·build 비용은 현재 측정 범위 밖 |

BFM 공용 정본 `docs/AGENT-BRIEF.md` §11-A에는 이미 합본 전수 1회와 재게이트 축소 기준이 있다. 그러나 **같은 앱 src/e2e끼리의 상류·내 변경은 앱 전체 게이트**, 공용 코드·설정은 전수로 판정한다. `scripts/ci-gate.mjs`도 프로젝트 및 소비처 단위로 선택하므로 BFM 내부의 독립 기능을 나누지 못한다. e2e-rail의 새 판정만으로 이 규약을 건너뛸 수는 없다.

과거 BFM 실측은 재게이트 501초 중 유닛 409초(약 82%), 합본 게이트 15.8분의 사례를 포함한다. 이 수치는 현재 벤치마크가 아니다. E2E 개선만으로 전체 대기시간이 얼마나 줄지는 단계 0에서 다시 잰다. 개인 `.claude/rounds/` 런북을 팀 공통 계약으로 배포하지 않는다.

## 3 반드시 유지할 검증 계약

1. **기존 full의 의미 유지.** 재사용 결과로 `kind: full` 실행을 만들거나 기존 `verify --require full`을 성공시키지 않는다. 신규 통합 검증은 별도 상태·정책이다.
2. **출처 보존.** 과거 실행의 HEAD·지문·시각·결과를 현재 후보 값으로 덮어쓰지 않는다. 새 판정이 원본 실행을 참조한다. 재사용으로 원본 증거의 나이를 초기화하지 않는다.
3. **판정 불가이면 확대.** 누락·손상된 증거, 미지원 정책, 동적 결합, 환경 불명은 생략 근거가 아니다. 필요한 범위를 재실행하고, 범위를 특정할 수 없으면 전수로 간다.
4. **개별 통과의 합은 통합 통과가 아니다.** A PASS와 B PASS만으로 A+B를 승인하지 않는다. 실제 합본 후보, 충돌 해결, 신규 테스트, 공유 입력, 상호작용을 따로 평가한다.
5. **Git·실행 대상 보호.** 검사 중인 후보를 rebase·cherry-pick·수정하지 않는다. 실제 테스트 서버가 후보 산출물을 제공하는지도 확인한다. 전후 해시만으로 실행 중 잠깐 바뀌었다 돌아온 상태까지 검출했다고 주장하지 않는다.
6. **범위·모드 보존.** dev/preview, 브라우저 project, test inventory, shard plan, 필터·retry·timeout 정책을 섞지 않는다. rerun·filtered·불완전 shard·진단 실행은 재사용 증거로 승격하지 않는다.
7. **AI 제안은 데이터.** 출력 형식과 근거를 검증하며, AI의 임의 명령·경로·신뢰 선언을 실행하지 않는다. 모델 오류·미응답은 자동 생략으로 처리하지 않는다.
8. **머신 락과 저장소 권한 유지.** heavy 배타·FIFO·개인 경로 보호를 유지한다. 새 실행 조정 기능이 기존 락을 우회하지 않는다. 원격 증거의 해시 일치는 작성자 신뢰의 증명이 아니다.

## 4 기능 소유권과 단계 경계

| 층 | 책임 | 첫 구현에서 제외 |
| --- | --- | --- |
| e2e-rail 코어 | E2E 실행 요청 중복 제거, 입력 manifest, 증거 조회·판정, 통합 E2E 계획 | 일반 CI 서비스, 원격 Git 호스팅 관리, 유닛 러너 구현 |
| 프로젝트 게이트 실행기 | typecheck·유닛·build·entry·E2E 순서, 후보 고정, 각 게이트 정책 적용 | e2e-rail의 검사 규칙 복제 |
| 통합 조정자 또는 CI | 변경 묶음 편성, Git 쓰기 소유권, 에픽 반영 직전 기준 ref 비교 | 사용자 승인 없는 자동 push·force push |
| 에이전트 스킬 | 현황 설명, 통합 계획 호출, 숨은 결합 점검, 실패 분류·보고 | 임의 증거 생성, 안전 점수만으로 생략 |

BFM 전용 경로·Jira·에픽 이름·검사 명령은 프로젝트 어댑터에 둔다. 코어는 Node 내장 모듈과 기존 peer 의존성 구조를 유지한다. TypeScript 그래프는 영향 분석 도구이며 완전한 테스트 입력 추적기로 간주하지 않는다.

## 5 단계별 구현 범위와 완료 기준

### 단계 0 측정과 판정 설명

**목표:** 시간을 무엇에 쓰는지와 전수 확대 이유를 수치로 남긴다. 실행 정책은 바꾸지 않는다.

구현 범위:

- 실행 요청에 후보 ID, 기준 base, 요청자, 앱·mode·검사 종류를 연결한다. 준비·큐 대기·build·테스트·분석·재시도 시간을 구분한다.
- 전수 이유를 `same-app-policy`, `shared-input`, `unknown-dependency`, `missing-evidence`, `upstream-moved` 등의 구조화된 코드와 근거 경로로 기록한다. 이름은 구현에서 확정한다.
- E2E 원장에는 E2E 측정만 추가한다. 프로젝트 게이트 실행기가 유닛·build·entry 시간을 별도 기록하고 같은 후보 ID로 합산한다.
- 후보당 전체 wall time과 실제 머신 사용시간을 별도로 계산한다. 병렬 단계 시간을 단순 합산해 사용자 대기시간으로 보고하지 않는다.

완료 기준:

- 성공·실패·취소·고아 실행의 시간과 상태가 구분되고, 기록할 수 없는 단계는 0초가 아니라 unknown으로 출력된다.
- 이전 원장 읽기와 현재 verify 판정은 그대로 동작한다. 신규 필드가 없어도 기존 실행을 누락하지 않는다.
- 동일 시나리오 반복 fixture의 합계·대기 계산을 검증한다. BFM에서는 대표 후보 최소 10건을 관측하는 것을 제안한다. 10건의 p95는 탐색값이며 성능 보증으로 쓰지 않는다.
- 측정 자체의 비용을 공개한다. 제안 목표는 게이트 시간의 5% 미만이며, 현재 달성한 수치가 아니다.

### 단계 1 동일 실행 중복 제거와 통합 후보 고정

**목표:** 검사 범위를 줄이지 않고 중복 실행 횟수와 상류 이동으로 버리는 비용을 줄인다.

1A 코어 구현:

- 같은 고정 후보에 대한 동일 요청은 한 producer가 실행하고, follower는 그 실행의 종료·결과를 기다린다. 이미 완료된 결과는 기존 verify가 같은 지문을 인정할 때만 재사용한다.
- 최초 지원은 **같은 머신·같은 사용자·같은 저장소 체크아웃의 읽기 전용 후보**다. 다른 worktree 사이 공유는 단계 2 이후로 미룬다.
- 요청 키에 후보의 정확한 코드 상태, 실제 경로/저장소 식별, 앱·mode, 검사 목록, 설정·실행 옵션, 실행 환경, 코어 정책을 포함한다. 한 항목이라도 다르거나 확인 불가하면 공유하지 않는다.
- preview 산출물은 producer가 생성·확정한다. build 전 요청 키만으로 통과를 선언하지 않는다. follower는 종료 후 후보·산출물 지문과 요구 범위를 다시 확인한다.
- follower 취소는 producer를 죽이지 않는다. producer 실패·취소·시간 초과는 모든 follower에 그대로 전달한다. 고아 회수 후 새 실행이 필요하면 새 attempt ID를 부여한다.
- 요청 상태와 결과를 원자적으로 게시하고 owner token·세대 번호로 이전 소유자의 늦은 성공 기록을 거부한다. 영구적으로 정확히 한 번 실행된다고 보장하지 않는다. 장애 시 중복 계산보다 거짓 성공을 막는 것이 우선이다.

1B 프로젝트 통합 구현:

- 조정자가 base와 준비된 변경 목록을 고정한 합본 후보를 만든다. 이 후보에 기존 전체 게이트를 한 번 실행한다. 이후 도착한 작업은 다음 후보로 보낸다.
- 후보 검사 도중 사용자 작업 트리를 변경하지 않는다. 무거운 게이트의 실행 위치는 BFM §11-A의 허용 행에 따라 정한다. 공유 표면 변경 트랙의 독립 전수 요구도 그대로 따른다.
- 큐 편성에 최대 대기·최대 묶음 크기를 두어 빠른 작업이 영원히 기다리지 않게 한다. 초기 값은 측정 후 프로젝트 정책으로 정하고 AI가 수시로 임의 변경하지 않는다.
- 통합 직전 remote base를 다시 확인한다. 원격이 움직였으면 후보를 새로 만들고 재판정한다. 단순 fetch와 push 사이 경쟁도 있으므로 서버의 원자적 ref 갱신 조건 또는 일반 non-fast-forward 거부를 최종 방어선으로 둔다. 실패 시 강제 push하지 않는다.
- 에픽에 직접 쓰는 경로가 여러 개이면 통합 큐만으로 재시작을 없앨 수 없다. 단일 통합 주체나 CI의 직렬 실행을 팀 운영에 연결해야 효과가 난다.

완료 기준:

- 동일 요청 5개를 동시 시작한 fixture에서 producer 실행 1회와 동일 원본 결과 참조를 확인한다. 다른 후보·옵션·프로젝트·mode는 합쳐지지 않는다.
- producer 종료, PID 재사용, 대기자 취소, 락 대기 중 후보 변경, 중간 기록 손상, 늦은 결과 게시의 회귀 테스트를 통과한다.
- A+B 검사 도중 C가 도착해도 A+B의 검사 내용은 바뀌지 않고 C는 다음 후보로 남는다. 상류가 바뀐 A+B 결과를 새 에픽 tip의 통과로 보고하지 않는다.
- 초기 범위에서는 증거 부족·dirty 트리·쓰기 중인 체크아웃은 기존 실행 경로 또는 명시적 거부로 보낸다. 무조건 영구 대기하지 않는다.
- `verify --require full`, complete shard set, last-green, 머신 락의 기존 테스트 판정은 변하지 않는다.

### 단계 2 전체 입력이 동일한 실행 증거 재사용

**목표:** SHA만 바뀐 경우 등 전체 실행 입력의 동등성이 확인되는 상황부터 지원한다. 기능별 부분 재사용은 아직 하지 않는다.

구현 범위:

- 기존 fingerprint를 유지하고 별도의 `inputManifest`와 `inputDigest`를 추가한다. 최초에는 clean Git tree 전체를 포함한다. 문서 변경도 tree를 바꾸면 재사용하지 않는 보수적인 시작점이다.
- 내용 외에도 경로·파일 모드·삭제·symlink 의미를 보존한다. submodule·외부 symlink·Git LFS 등을 정확히 처리하지 못하면 미지원으로 거부한다. ignored 출력과 ignored 실행 입력을 구분한다.
- 앱·테스트·fixture·global setup·설정의 import·lockfile·설치된 의존성 정합성·Node·Playwright·브라우저·OS/arch·실행 옵션·환경 계약을 기록한다. lockfile만 같다는 이유로 설치된 패키지까지 동일하다고 추정하지 않는다.
- preview는 build 입력과 실제 산출물 해시를 함께 확인한다. commit ID를 주입하는 빌드나 외부 파일·시간·환경에 의존하는 빌드는 해당 입력까지 일치하거나 검증된 hermetic 계약이 있어야 한다. `HEAD`만 지문에서 제거하지 않는다.
- 실서버 데이터·계정 상태·시간·네트워크 등 통제되지 않은 입력이 있는 테스트는 초기 재사용 대상에서 제외한다. TTL만으로 동일 환경을 증명할 수 없다. 통제된 mock/fixture 환경부터 시작한다.
- 원본 실행 뒤 입력 변경·오염·취소가 없었다는 기록이 있어야 한다. 구형 원장에 신규 필드가 없으면 현재 파일로 과거 입력을 역산하지 않고 재사용 불가로 처리한다.
- 재사용 판정의 재사용이 반복되어도 참조는 실제 원본 실행까지 추적한다. 순환·누락·지원하지 않는 정책 경로를 거부하며, 유효기간은 원본 실행 시각과 현재 정책으로 계산한다. 중간 판정이 원본의 나이나 검사 범위를 늘릴 수 없다.
- 같은 사용자 로컬 증거만 우선 지원한다. 다른 머신/동료의 원장은 저장소 ID와 해시만으로 신뢰하지 않는다. CI 실행 출처·artifact digest·허용된 producer를 검증하는 교환 계층은 단계 4에서 다룬다.

완료 기준:

- 동일 tree의 다른 커밋에서도 실행 입력·산출물·환경·목록이 모두 같을 때만 새 재사용 판정이 성공한다. 한 항목 변경 시 재실행 이유를 반환한다.
- commit-dependent build, ignored env, 설정 import, 브라우저 버전, 외부 데이터, 파일 삭제·이름 변경, 미커밋, 불완전 manifest의 음성 테스트가 거짓 재사용을 만들지 않는다.
- 새 판정은 원본 run ID와 원본 실행 시각을 인용한다. 기존 full verify는 다른 fingerprint에서 계속 stale이다. last-green과 기존 shadow streak를 이동시키지 않는다.
- 신규 정책·schema는 명시적 지원 버전만 허용한다. 현재 `currentPolicy`의 숫자 비교를 신규 증거 호환성 규칙으로 그대로 복제하지 않는다.

### 단계 3 통합 영향 분석과 테스트별 증거

**목표:** 같은 앱 안의 독립 변경에서도 재실행할 부분을 구분한다. 단계 2의 동일 입력 증명보다 강한 가정이 필요하므로 처음에는 report-only로 동작한다.

구현 범위:

- merge-base, 각 변경의 출발·완료 commit, 실제 합본 candidate, 충돌 해결 diff를 입력으로 받는다. 단순히 최근 두 HEAD를 비교하지 않는다. 공통 조상을 확정할 수 없으면 전수로 간다.
- 기준과 후보 양쪽의 의존성을 비교한다. 새 import, 삭제된 간선, rename, 동적 import, CSS·asset·glob·전역 setup, test project dependencies를 반영한다. 과거에 관측된 coverage는 결합을 추가하는 근거로 쓸 수 있지만 미관측을 독립성의 증명으로 쓰지 않는다.
- 원장의 최소 단위를 spec×project에서 안정적인 test ID·실행 목록·결과로 보강한다. 초기 재사용은 모든 대상 테스트가 실제 실행되어 통과한 증거만 받는다. skip/todo/expected-failure/flaky의 취급은 명시 정책으로 정하며, 초기에는 재사용 제외한다.
- 전역 입력은 모든 테스트에 연결한다. 인증·셸·공용 fixture·환경·빌드 설정·미해석 경로는 full 확대 조건을 유지한다. 파일 경로가 다르다는 사실만으로 독립이라 판정하지 않는다.
- AI는 두 변경이 공유하는 query key·storage key·이벤트·라우트 문자열·팝업 콜백·API 상태를 검토한다. `file:line`, 연결되는 test, 이유를 구조화된 결과로 반환한다. 기본 계산에서 테스트를 제거하거나 required full을 낮출 수 없다.
- AI 검토는 candidate+plan+입력 manifest+검토 규칙 버전에 묶는다. 후보나 목록이 바뀌면 검토도 stale이다. 미응답·잘못된 형식·근거 불충분이면 불확실한 범위를 확대한다.
- 모델 하나의 제한된 검토가 기본이다. 두 번째 모델은 충돌 해결·공유 상태·첫 검토 불일치 등 정책상 불확실한 경우에만 요청한다. 검토 시간·토큰도 비용에 포함한다.

범위 계산 계약:

```text
U = 후보에서 실제 열거한 모든 test × project 및 필요한 setup 의무
R = 후보에서도 유효하다고 정책이 인정한 원본 증거가 덮는 의무
F = 직접 영향 ∪ 통합 상호작용 ∪ 충돌 해결 ∪ 신규/변경 테스트
    ∪ 필수 smoke/setup ∪ AI 추가 ∪ 증거/분석이 불명확한 의무
E = (U - R) ∪ F
최종 재사용 = R - E
```

재실행 E가 재사용 R보다 우선한다. **ΔA ∩ ΔB만 실행하는 방식은 금지**한다. 각 의무가 이번 실행 또는 허용된 원본 증거로 연결되는지 검사하고, 구멍이 있으면 통합 verified를 반환하지 않는다. E가 비었다고 자동 통과하지 않는다. U 열거·필수 smoke·정책 유효성을 다시 확인한다.

완료 기준:

- §8의 fixture·변이에서 생략 대상으로 잘못 분류한 실패가 0건이어야 한다. 독립 변경 fixture에서는 적어도 하나의 기존 검사 재사용을 실제로 보여야 한다. 항상 full인 구현도 기능 완료로 보지 않는다.
- 합본에서만 발생하는 상태 충돌을 AI 또는 보수적 정책이 확대하도록 확인한다. 자동 분석으로 찾지 못하면 전역 입력/계약을 추가하거나 해당 범위를 재사용 대상에서 제외한다.
- 원본·후보 모두 성공한 표본만으로 정확도를 평가하지 않는다. 전체 게이트 대조와 인위적 결함 주입을 함께 사용한다.
- report-only 기간에는 기존 BFM 전체 게이트를 계속 실행한다. 단계 3이 통과해도 프로젝트 규약이 바뀌기 전에는 병합 승인 근거를 대체하지 않는다.

### 단계 4 프로젝트 게이트 연결과 제한된 활성화

**목표:** E2E 바깥의 중복도 줄이고, 두 에이전트 런타임에서 사용자가 매번 명령하지 않아도 같은 정책을 따르게 한다.

구현 범위:

- 프로젝트 실행기는 typecheck·유닛·build·entry·E2E별 입력 manifest와 결과를 연결한다. E2E 원장을 일반 테스트 결과로 오염시키지 않는다.
- 유닛 테스트 선택·재사용은 해당 러너의 지원과 glob/파일 스캔 테스트의 동적 입력까지 별도 검증한다. E2E 그래프 결과를 유닛 생략에 바로 쓰지 않는다.
- 빌드 산출물을 불변 artifact로 보관해 재사용하며, 후보 소스와의 provenance·digest를 확인한다. 현재 dist mtime 검사만으로 artifact 동일성을 대신하지 않는다.
- 다른 머신 증거는 신뢰하는 CI producer와 저장소·workflow·revision·artifact 검증을 통과한 것만 받는다. JSON 다운로드만으로 동료 통과를 승인하지 않는다. 자체 인증 프로토콜보다 기존 CI 접근 제어를 우선하며, 미지원 플랫폼은 로컬 범위로 제한한다.
- `autopilot`, `gate`, `measure`에 실행 중인 동일 후보 대기·통합 계획·새 보고 상태를 연결한다. Claude 정본 skills/references를 수정하고 `sync:codex`로 반영한다. 훅 신뢰나 사용자 도구 권한을 우회하지 않는다.
- Claude Stop 훅과 스킬이 기존 verify만 보고 신규 통합 판정을 무시해 다시 full을 요구하는 반복을 방지한다. 기본 정책은 기존 판정을 유지하고, 명시적으로 활성화한 프로젝트에서만 동일한 integration verifier를 호출하도록 연결한다. 훅이 임의 프로젝트 설정·의존성 JS를 자동 실행하지 않도록 0.3.3 보안 경계를 보존한다. Codex에는 Claude 전용 Stop 강제를 구현한 것처럼 설명하지 않는다.
- 문서 설명에는 검사를 실행하지 않는다. 코드 작업도 setup 불완전·후보 불명·도구 없음이면 원인을 보고한다. 앱 종료 후 daemon 감시·예약 작업은 범위 밖이다.

활성화 기준:

- 프로젝트 정책에 적합한 부분만 opt-in한다. BFM의 최초 합본 전수와 상류 이동 후 재게이트를 서로 다른 정책으로 다룬다. 초기에는 **최초 합본 full 유지, 이후 재게이트 최적화**를 권장한다.
- 새로운 integration shadow는 기존 selection shadow와 분리하고 앱·mode·정책별로 누적한다. 기존 승격 상태를 자동 승계하지 않는다.
- 제안 최소 평가량: 정상 후보 20건 이상, 독립/결합/충돌/설정 변경을 포함하고 §8의 결함 주입 전건을 검증한다. 20건은 절차 시작점이며 안전성을 통계적으로 증명하는 수치가 아니다.
- 동일 조건에서 총 wall time·머신 사용시간·실행 횟수·AI 비용을 비교한다. 제안 성능 목표는 대표 병목 시나리오 p50 20% 이상 절감, p95 악화 없음이다. 표본 수와 분포를 함께 제시하고 목표 미달이면 원인 측정 후 활성화를 보류한다.
- 누락 1건, 증거 변조 허용, 검사 후보와 반영 후보 불일치는 즉시 해당 정책을 report-only로 내린다. 기존 full 경로로 복구하고 이전 증거는 조사용으로 보존한다.
- 구버전 코어가 신규 판정을 full로 오인하지 않는 혼합 버전 테스트를 통과한다. 기능을 끄면 기존 검증이 그대로 작동하며, 개인 설치·공유 저장소 설정·CI 사이 정책 차이는 status에서 드러나야 한다.

## 6 데이터와 CLI 계약 초안

구현 전 Claude가 다음 데이터의 소유권·직렬화·schema와 종료 코드를 확정한다. 아래는 필수 정보이며 완성된 JSON schema가 아니다.

| 기록 | 필수 정보 |
| --- | --- |
| candidate | repo identity, base SHA, 순서 있는 source SHA 목록, candidate SHA/tree, 충돌 해결 입력, 생성 방식 |
| request | candidate, app/mode, inventory digest, 옵션, runtime/environment 계약, policy, 요청자, producer/follower |
| input manifest | schema, 전체/부분 범위, 경로와 content digest, global inputs, dependency graph digest, 환경 식별, unresolved 목록 |
| run evidence | 원본 run ID·시각·fingerprint, 입력 manifest, 실제 실행 inventory와 결과, artifact digest, producer 출처, 오염 여부 |
| integration plan | candidate, 요구 의무 U, 재사용 후보 R, 실행 E, 확대 이유, AI 검토 결합 키, policy |
| decision | plan ID, 원본 evidence 참조, 이번 run 참조, 누락 의무, verified/insufficient/stale/blocked, 실제 실행량과 재사용량 |

저장 규칙: 신규 조정·판정은 실행 `ledger.jsonl`과 별도 파일/원장에 기록한다. 원본 run을 복제해 실행 건수를 부풀리지 않는다. atomic write, path containment, symlink 방어, private 권한, 읽기 크기 제한, 알 수 없는 schema 거부를 적용한다. 환경 비밀값·인증 토큰을 기록하지 않는다. 비밀값의 단순 해시도 저엔트로피 추측에 취약할 수 있으므로 재사용은 통제된 환경 식별자로 제한하고, 필요한 경우 별도 위협 모델을 검토한다.

인터페이스 제안:

```text
e2e-rail integration plan --candidate <sha> --base <sha> --app <app> --mode preview
e2e-rail integration verify --plan <id> --json
e2e-rail integration status --candidate <sha> --json
```

계획 생성·검증은 임의 Git merge/push를 수행하지 않는다. 실제 테스트는 기존 `e2e-rail run` 경로를 통과한다. plan을 실행으로 연결하는 옵션·필수 필드·종료 코드는 기존 `select`/`verify`와 충돌하지 않게 확정하고 CLI help·계약 테스트를 함께 만든다.

보고 예시도 다음처럼 기존 full과 구분한다. 숫자는 형식 예시이며 측정값이 아니다.

```text
integration: verified — policy <id>, candidate <sha>, mode preview
executed: 18 test-project obligations — run <id>
reused: 82 test-project obligations — source runs <ids>, oldest <time>
unknown: 0
full on this candidate: not run
project gate: pending | satisfied under <policy>
```

기존 full 기반 last-green은 유지한다. 새 통합 정책의 기준점이 필요하면 별도 marker를 만든다. 모든 테스트 의무가 채워졌어도 검증하지 않은 유닛·build·entry를 포함해 프로젝트 전체가 통과했다고 보고하지 않는다.

## 7 AI 판단과 자동화 평가

AI에게 주는 입력은 candidate diff, 기계가 계산한 연결, 기존 증거 요약, 불확실한 영역이다. 전체 저장소를 매번 읽게 하기보다 관련 범위를 읽고, 필요할 때 확대한다. agent review 결과 자체도 후보와 정책이 동일하면 재사용할 수 있지만 원본 테스트 증거를 대체하지 않는다.

| 평가 요청 | 기대 동작 |
| --- | --- |
| 스킬명을 언급하지 않은 코드 수정 | 변경 검증 후 통합 대상이면 계획 조회, 동일 실행 대기 또는 필요한 검증 수행 |
| 이미 실행 중인 동일 후보에 대한 결과 요청 | 새 full을 시작하지 않고 원본 실행 상태·결과를 사용 |
| 동료 변경 합치기, 숨은 공유 storage key 존재 | 연결 근거 제시, 영향 테스트 추가 또는 full 확대 |
| 문서 설명만 요청 | 테스트·큐 등록·Git 쓰기 없음 |
| 테스트하지 말라는 사용자 지시 | 실행하지 않고 미검증/통합 대기 상태 명시 |
| 원장 없음·훅 미신뢰·도구 없음·AI 검토 실패 | 통과를 주장하지 않고 가능한 정적 판단과 미검증 사유 보고 |
| 후보가 검토 후 변경됨 | 과거 계획·검토 결과로 완료하지 않고 재계산 |

Claude와 Codex에서 같은 fixture와 기대 상태로 평가한다. CLI 계약 테스트, 실제 브라우저 테스트, 에이전트 자동 선택, 데스크톱 SessionStart 주입은 각각 다른 증거다. 0.3.3의 기존 데스크톱 주입 검증을 새 기능의 자동 수행 검증으로 재사용하지 않는다. 실제 훅 변경 시 해당 런타임의 신뢰 절차를 따른다.

fixture는 각각 정상 대조군과 실패 대조군을 갖는다. hash 비교 제거, global-input 무시, AI 제거 허용, inventory 일부 누락, 후보 검증 생략의 변이를 심어 테스트가 이를 잡는지 확인한다. stub만으로 완료하지 않고 실제 Playwright 러너 계약을 검증한다. 브라우저 결합·서버 provenance 항목에는 실제 페이지와 브라우저를 쓰며 runner-only 테스트와 구분한다.

플러그인의 기존 전체 단위·계약 스위트를 기준선과 변경 후에 실행한다. 새 테스트 수가 늘었다는 사실보다 기존 판정의 보존과 위 음성 사례의 검출이 완료 기준이다. Playwright 지원 버전의 목록 형식 차이도 현재 CI 매트릭스에 맞춰 확인한다.

## 9 Shadow 평가와 성능 측정

동일 후보에서 새 정책의 계획을 먼저 고정하고 기존 전체 게이트를 실행한다. 전체 결과를 본 뒤 계획을 수정해서 hit로 세지 않는다. 전체 검사가 발견한 실패 중 새 계획의 실행·허용 증거가 덮지 못한 것을 miss로 기록한다. 이미 flaky하거나 환경 장애로 실패한 경우도 원본은 보존하고 분류 근거를 남긴다. 편의상 실패를 삭제하지 않는다.

한 후보의 통과는 일반적인 독립성 증명이 아니다. 전체 게이트가 탐지하지 못하는 결함은 shadow도 찾지 못한다. 이를 보완하기 위해 §8의 결함 주입을 병행하고, 활성화 후에도 주기적·표본 전체 검증과 필수 전체 검증 경계를 유지한다. 주기·표본 비율은 프로젝트 정책에 명시한다.

비교 지표:

- 후보 등록→반영 가능까지 wall time, 실제 CPU/머신 점유시간, 큐 대기시간.
- 후보당 full 횟수, 중복 요청 병합 수, 무효화되어 버린 검사 시간.
- 실행/재사용 test-project 의무 수, full 확대 이유별 빈도, 미지원 비율.
- AI 검토 시간·토큰·확대 건수·기계 판정과 불일치 건수.
- miss, flaky, 오염된 실행, 잘못된 증거 수용 건수.

기준선과 제안 정책은 같은 머신·worker·mode·브라우저·입력 상태에서 비교한다. cold/warm cache와 부하 차이를 기록하고 실행 순서를 교대한다. report-only의 예상 절감과 실제 실행을 생략해 측정한 절감을 구분한다. 긴 게이트를 단순히 다음 시점으로 미뤄 완료 보고 시간만 줄인 경우는 절감으로 세지 않는다.

## 10 변경 파일과 구현 순서 제안

아래 신규 파일명은 책임 분리를 설명하기 위한 예시다. 기존 모듈에 자연스럽게 들어가는 작은 변경이면 불필요한 계층을 만들지 않는다.

| 단계 | 기존 접점 | 신규 책임 예시 | 반드시 함께 검증 |
| --- | --- | --- | --- |
| 0 | `src/run.mjs`, `src/measure.mjs`, commands, ledger 읽기 | gate timing adapter/분석 결과 | 구형 원장·실패·취소 시간 |
| 1 | run, lock, status, CLI | `execution-registry.mjs`, 후보 계약·프로젝트 큐 예제 | 멀티프로세스·고아·원본 결과 공유 |
| 2 | fingerprint, ledger, verify 경계 | `input-manifest.mjs`, `evidence.mjs`, 별도 재사용 판정 | 내용/환경 음성 사례·기존 full 불변 |
| 3 | select, graph, spec-index, report parser | `integration-plan.mjs`, `integration-verify.mjs` | inventory 완전성·합본 회귀·AI 실패 |
| 4 | skills, references, sync-codex, CI templates | 프로젝트 게이트 어댑터·증거 교환 | 양 런타임·CI 출처·BFM shadow |

권장 첫 PR 범위는 **단계 0과 1A**다. 1B는 프로젝트 연동 예제와 운영 계약부터 만든다. 단계 2 이후의 재사용 판정을 같은 PR에 몰아넣지 않는다. 각 단계에서 문서·help·fixture·회귀 테스트·실측 보고를 함께 남긴다. 버전 번호는 교차검증 뒤 확정하며, 문서 작성만으로 현재 버전을 올리지 않는다.

## 11 Claude 교차검증 요청

구현 전에 다음 질문을 각각 **채택 / 수정 / 보류**로 판정하고 코드 근거, 반례, 결정 내용을 기록한다. 단순 동의나 계획 재서술로 끝내지 않는다.

1. 실제 최신 코드에서 동일 요청의 중복 실행이 발생하는 경로와 빈도가 있는가? 이미 기존 verify 호출만으로 해소할 수 있는 부분은 어디인가?
2. 큐를 e2e-rail 코어에 둘 부분과 프로젝트 조정자에 둘 부분이 적절한가? 에픽에 쓰는 주체를 통제하지 못할 때도 유효한 최소 구현은 무엇인가?
3. phase 1 요청 키가 build 전후 입력·옵션·환경을 충분히 구분하는가? 실제 후보 불변성을 어떻게 보장하는가?
4. 전체 tree가 같아도 Git metadata·설치 패키지·외부 데이터가 결과를 바꾸는 반례를 단계 2가 거부하는가?
5. 테스트별 의존성 경계를 어디까지 신뢰할 수 있는가? 정적 그래프만으로는 부족한 영역을 full로 남기는가?
6. 기존 spec 집계에서 사라지는 skip/expected failure 정보를 어떤 schema로 보완할 것인가?
7. AI 분석이 검토 비용보다 큰 절감을 주는가? 검토 생략·재사용·두 번째 모델 호출의 결정 조건은 무엇인가?
8. 새로운 evidence/integration schema가 기존 verify·shard·shadow·last-green의 의미를 바꾸지 않는가?
9. BFM §11-A에서 유지할 조건과 나중에 수정할 조건을 구체적으로 나눴는가? 유닛이 지배하는 후보에 E2E 최적화만 적용하고 성공을 과장하지 않는가?
10. 다른 사용자/머신의 증거를 받는 신뢰 경계와 보관·삭제·비밀정보 처리가 충분한가?

교차검증 산출물은 같은 디렉터리의 `2026-10-14-integration-gate-reuse-review.md`, 확정 구현 계획은 `docs/superpowers/plans/`에 작성하는 것을 제안한다. 독립 검토 모델을 실제로 사용했다면 실행 환경·입력 범위·검토 결과를 기록하고, 사용하지 않았다면 교차검증 완료라고 표시하지 않는다.

후속 구현 완료 보고에는 기준/완료 commit, 변경 정책, 단계별 통과·보류, §8 테스트 결과, 실제 명령과 원장 증거, 비용 비교, 남은 위험, rollout/rollback 상태를 포함한다. 이번 보고서는 실행 결과를 포함하지 않는다.

## 12 참고 근거

- e2e-rail 현재 구현: `src/{fingerprint,verify,ledger,run,lock,select,graph,measure}.mjs`, `src/util/git.mjs`, `src/commands/`, `skills/{autopilot,gate,measure}/SKILL.md`.
- 기존 설계: [e2e-rail 설계 스펙](./2026-10-07-e2e-rail-design.md). 초기 문서의 구현 전 상태·버전·스킬 수는 역사적 기록이며 현행 판단은 코드와 0.3.3 검증 기록을 따른다.
- 자동화 선행 설계: [Agentic autopilot handoff](./2026-10-12-agentic-autopilot-handoff.md), [검토 및 런타임 검증](./2026-10-12-agentic-autopilot-review.md).
- BFM 별도 저장소: `docs/AGENT-BRIEF.md` §11-A, `scripts/ci-gate.mjs`, `scripts/gate-guard.mjs`. 구현 시 최신 파일을 다시 확인한다.
- [GitHub merge queue 공식 문서](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue): 최신 base와 선행 변경을 포함한 후보 검증의 참고 구조. GitHub Actions에서는 `merge_group` 이벤트 연동이 필요하다. merge limits 설정 자체가 검사 build를 하나로 합치는 기능은 아니다. 이 보고서는 BFM이 GitHub merge queue를 사용하거나 사용할 수 있다고 가정하지 않는다.

자가개선: 해당 없음. 신규 기능 설계이며 기존 규약의 수정·승격을 수행하지 않았다.
