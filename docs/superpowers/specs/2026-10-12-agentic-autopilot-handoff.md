# e2e-rail 자동 운영 검증 및 구현 인계 보고서

작성일: 2026-10-12 KST  
대상: 다음 검토·구현 모델  
저장소: https://github.com/sh5623/e2e-rail  
검토 기준: v0.2.3 · `63c2bfed089d5fc3012bd2c33e4bcdd2026973b5`

## 1. 목적과 결론

사용자가 원하는 제품은 Claude Code 또는 Codex에 설치한 뒤, 프로젝트 최초 설정을 마치면 일반적인 개발 요청에 필요한 E2E 판단·실행·검증이 따라오는 플러그인이다. 사용자가 작업마다 `init`, `select`, `gate`, `measure`, `shadow`를 골라 호출하는 경험을 기본으로 삼지 않는다.

목표 경험은 다음과 같다.

> 사용자가 “주문 검색 조건 수정해줘”라고 요청한다. 에이전트가 구현하고, 변경 영향을 검토하고, 적절한 테스트를 실행한다. 실패하면 근거를 조사하고, 현재 코드에 유효한 검증 결과를 보고한다. 사용자는 E2E 스킬명을 지시하지 않는다.

현재 CLI는 선택·원장·지문 검증·락·샤드의 기반을 갖췄다. 다음 우선순위는 **자동 진입, 프로젝트 준비 상태 확인, 작업 단계에 맞는 실행 계획, 검토 기록의 유효성 확인**을 연결하는 것이다. 실패 진단과 매핑 개선은 이 흐름 안에서 사용한다.

이 문서의 기능명·상태·데이터 구조는 제안이다. 구현자는 현재 코드와 두 런타임의 실제 기능을 독립 검증하고, 채택·변경·보류한 항목의 이유를 기록한다. 이 문서 작성 요청 자체가 추가 커밋·태그·푸시·사용자 환경 설치를 승인한 것은 아니다. 구현 및 배포는 다음 세션에서 받은 사용자 요청 범위를 따른다.

### 검증 이력과 범위

- v0.2.3: 단위 테스트 307개, 실제 Playwright 러너 계약 테스트 4개 통과. GitHub CI의 Node 20·22 및 Playwright 1.56 계약 작업도 통과했다.
- 락 공정성은 별도 프로세스·타임아웃·종료·고아 복구·배타성 테스트와 변이로 검증했다. 원장 검증 정책은 2다.
- 2026-10-09 BFM 분석: 149 spec, 186 라우트 진입점, 미해석 spec 13개. 주문배송조회 단일 파일 변경 가정은 30 spec, 주문카트는 24 spec을 선택했다.
- 위 BFM 수치는 과거 소스의 **선택 분석**이다. 실제 브라우저 실행 시간 단축이나 누락률을 입증한 수치는 아니다. 현재 소스의 수치가 필요하면 다시 측정한다.
- Claude·Codex에 설치한 상태에서 일반 개발 요청만으로 전체 절차가 자동 수행되는지는 아직 종단 간 평가하지 않았다. CLI 테스트 통과를 이 자동성의 증거로 사용하지 않는다.

## 3. 사용자에게 보이는 자동 동작 계약

### 최초 한 번

플러그인이 프로젝트·Playwright·TypeScript·앱 구성을 탐지하고 초기 실행 정책을 제안한다. 기존 사용자 지시와 레포 규칙을 우선하며, 필요한 설정과 허용 범위를 묶어서 확인한다. 이미 승인된 범위를 매 실행 다시 질문하지 않는다. 런타임의 도구 권한이나 훅 신뢰 절차를 우회하지 않는다.

### 이후 개발 작업

1. 현재 작업이 소스·테스트 동작을 바꾸는지 확인한다. 단순 설명·문서 요청에 E2E를 자동 실행하지 않는다.
2. 프로젝트 준비 상태와 현재 코드의 유효한 검증 결과를 확인한다.
3. 필요한 변경 범위만 분석하고, 정적 선택기가 놓칠 수 있는 관계를 에이전트가 검토한다.
4. 개발 중에는 정책에 맞는 선택 실행을 한다. 섀도 기간의 최종 통합 전수는 유지한다.
5. 실패하면 원본 로그를 보존하고 제한된 진단을 수행한다. 원인을 고치고 다시 선택·검증한다.
6. 완료 보고는 실행 종류, 현재 코드에 대한 검증 여부, 남은 전수 검증을 명시한다.

사용자가 알아야 할 결과나 설정 불확실성이 생겼을 때만 개입을 요청한다. 스킬 이름·명령 순서를 사용자가 기억하게 하지 않는다. 자동화 범위는 활성 개발 작업 안이다. 앱 종료 후 감시나 예약 실행은 별도 기능·권한으로 다룬다.

## 4. 개인 플러그인과 프로젝트 실행기 배포

BFM에서 전달된 경계는 **개인 도구를 BFM의 package.json·lockfile·공유 브리프에 임의로 넣지 않는다**는 것이다. 현재 init의 프로젝트 devDependency 설치 방식과 이 경계를 먼저 조정해야 한다. 단순히 승인 질문만 없애서는 안 된다.

| 실행기 방식 | 장점 | 검증할 비용 |
| --- | --- | --- |
| 현재 방식인 프로젝트 버전 고정 | 팀·CI가 같은 버전 사용, 재현성 명확 | 프로젝트 파일 변경 필요, 개인 플러그인 기본값에는 부적합할 수 있음 |
| 플러그인에 CLI를 함께 배포 | 설치 후 개인 사용에 유리, 프로젝트 의존성 변경 불필요 | Claude·Codex 양쪽 배포에 같은 core 포함, 실행 경로·버전·상태 저장 분리 필요 |

**권고:** 개인 자동 운영에는 플러그인 포함 실행기를 우선 검토하고, 팀·CI 연동은 명시적으로 프로젝트 버전을 고정하는 선택지로 둔다. 어느 쪽이 실제 기본값이 될지는 구현 전 판정 사항이다.

현재 Claude 플러그인 루트에는 CLI 소스가 있지만 Codex 패키지 `plugins/e2e-rail/`는 스킬·참조·훅 중심이다. 실행기를 번들링하려면 복제 방식을 새로 검증해야 한다. `createRequire`로 호스트의 TypeScript·Playwright를 빌리는 현재 구조와 CLI 버전 읽기 경로도 함께 점검한다.

실행기 루트, 분석 대상 레포·앱 루트, 설정 저장 위치, 실행 원장 위치를 명시적으로 분리한다. 개인 모드의 설정·원장은 사용자 전용 경로를 사용할 수 있어야 하며, 프로젝트의 `.gitignore` 변경을 필수로 만들지 않는다. 외부 상태 경로 지원은 현재 구현을 확인한 뒤 도입한다. 서로 다른 레포·워크트리의 선택 목록과 원장이 섞이면 안 된다.

## 5. 자동 진입과 런타임별 지원 검증

공통 core 위에 Claude·Codex 연결 계층을 얹는다. 다음 역할을 구분한다.

| 계층 | 담당 |
| --- | --- |
| 훅·런타임 연결 | 준비 상태 확인, 변경 표시, 필요한 시점에 에이전트로 제어 전달 |
| 통합 스킬 | 작업 단계 해석, 영향 분석, 실패 원인 가설, 다음 행동 선택 |
| CLI | 파일·지문·목록 검사, 락, 실제 실행, 원장, 검증 결과의 의미 강제 |
| 프로젝트 정책 | 개발 중 선택 실행과 최종 전수의 위치, 비용·진단 한도 |

SessionStart에서는 가벼운 탐지와 상태 안내만 수행한다. 긴 빌드·전수 E2E를 동기 세션 훅에 넣지 않는다. 코드 변경은 모아서 처리하고 같은 코드에 중복 실행하지 않는다. 읽기 도구 호출마다 스캔하거나 파일을 저장할 때마다 E2E를 시작하지 않는다.

작업 마무리 검증을 어떤 이벤트에 연결할지는 각 런타임에서 실제 지원 여부를 확인한다. 같은 이름의 이벤트가 두 런타임에서 같은 의미·출력·차단 권한을 갖는다고 가정하지 않는다. 지원하지 않는 지점은 스킬 안내나 명시적 CI 진입점으로 대체하고, 강제되는 범위와 모델 준수에 의존하는 범위를 구분해 설명한다.

구현 전 아래 지원표를 실제 설치 버전 기준으로 채운다.

| 확인 항목 | Claude Code | Codex |
| --- | --- | --- |
| 플러그인 설치·갱신 뒤 활성화 시점 | 확인 필요 | 확인 필요 |
| 사용자 스킬명 호출 없는 자동 진입 | 실제 대화로 평가 | 실제 대화로 평가 |
| SessionStart 출력 주입 | 현재 훅 있음, 실행 확인 필요 | 현재 훅 있음, 신뢰 승인 후 실행 확인 필요 |
| 변경 관측·작업 마무리 연결 | 지원 이벤트·제약 조사 | 지원 이벤트·제약 조사 |
| 중단·재개·컨텍스트 축약 | 대기·검증 상태 복구 평가 | 대기·검증 상태 복구 평가 |
| 직접 Playwright 실행 감지 | 가능한 범위 조사 | 가능한 범위 조사 |

훅을 설치하면 모든 셸 명령이 가로채진다고 주장하지 않는다. 임의 셸 문자열을 자동 치환해 실행하지 않는다. 원장을 거치지 않은 실행은 검증되지 않은 것으로 다루고, 필요한 경우 정상 CLI 경로로 다시 검증한다.

## 6. 통합 실행 계획과 에이전트 검토 기록

사용자에게는 하나의 자동 운영 흐름을 제공하고 기존 스킬들은 내부 절차로 재사용한다. `autopilot`, `plan`, `doctor`, `triage`라는 이름은 설명용 후보이며 현재 명령이 아니다.

실행 상태는 준비 필요 → 변경 없음 또는 계획 필요 → 검토 필요 → 실행 대기 → 실행 중 → 진단 필요 또는 검증 완료로 구분할 수 있다. 원장과 지문을 근거로 전이하며, 재진입 시 같은 작업을 다시 큐에 넣지 않는다. 중단된 실행을 성공으로 기록하지 않는다. 작업 단계가 불명확하면 기존 전수 규칙을 임의로 완화하지 않는다.

제안하는 계획·검토 기록에는 다음을 포함한다.

- 기준 커밋 SHA, 현재 codeId, 앱, 실행 모드·브라우저 프로젝트, 선택 목록 해시.
- 실행기·선택 규칙·검토 체크리스트 버전과 설정 지문.
- 선택 이유, 에이전트 추가 항목, 근거 소스 위치, 확인하지 못한 관계.
- 개발 중 검증인지 통합 게이트인지, 수행할 실행과 아직 남은 전수.
- 관련 실행 ID와 완료·실패·중단 상태.

코드·선택 목록·관련 설정이 바뀌면 검토 기록을 무효화한다. 현재 자동 재선택에서 예전 `--add`를 유지하더라도, 새 변경에 대한 영향 분석 완료까지 보장된 것은 아니다. 새 변경을 다시 검토한 뒤 실행하도록 연결한다.

기록 구조가 유효하다는 사실과 에이전트의 추론이 옳다는 사실은 다르다. 누락 탐지 평가는 별도로 수행한다. 에이전트가 만든 불확실한 숫자 점수로 테스트를 제외하지 않는다.

## 7. 에이전트 판단의 범위

정적 선택기는 기존처럼 불확실하면 전수로 넓힌다. 에이전트는 모달 오프너·문자열 이동·URL 상태·동적 등록 같은 관계를 찾아 테스트를 추가할 수 있다. 전수 대상으로 판정된 앱을 추측만으로 좁히지 않는다.

반복해서 발견하는 관계는 구조화된 근거로 재사용할 수 있다. 예를 들어 “이 모달은 주문배송조회와 주문카트에서 열린다”를 소스 위치·내용 해시와 함께 기록한다. 관계의 근거가 변경되면 재검토하며, 초기 버전에서는 재사용 기록을 **테스트 추가 근거**로만 사용한다. 과거 실행에서 관측되지 않았다는 이유로 제외하지 않는다.

허용된 자동 판단: 테스트 추가, 전수 확대, 기존 결과 유효성 확인, 제한된 진단, 원인별 다음 실행 제안·수행. 사람이 정할 정책: 초기 프로젝트 변경 허용 범위, 전수 대체를 위한 신뢰 승격, 테스트 제외 권한, 워커 상한·외부 실행 자원. 이미 정한 정책은 반복 확인하지 않되 런타임 권한 제한은 따른다.

## 8. 효율 개선과 실패 분석

### 선택이 넓어지는 원인 진단

미매핑 개수뿐 아니라 원인과 실제 반복 비용을 함께 출력한다. 동적 goto, 별칭, 라우트 형태, 공용 fixture, 전역 결합을 구분하고 관련 파일을 제시한다. 원장에 실행 시간이 없으면 시간 절감량을 추정해 사실처럼 쓰지 않는다. spec 개수 감소와 벽시계 시간 감소도 구분한다.

미해석 spec이나 전체 실행 사유를 제거할 때는 정상·오류·빈 상태·모바일 등 그 spec의 원래 검증 범위를 유지한다. 테스트 경로를 단순하게 보이게 바꿔 누락시키는 수정을 허용하지 않는다. 자동 수정 제안은 선택 결과 전후와 근거를 함께 남긴다.

### 실패 후 다음 행동

실패 로그·요청·trace·관련 변경을 묶어 관측 사실, 원인 가설, 다음 검증을 구분한다. 공통 목 실패, 앱 동작 회귀, 테스트 기대값 오류, 실행 환경 문제를 섣불리 확정하지 않는다. 단독 재실행 성공은 flaky나 부하 원인의 증명이 아니다.

진단 횟수·시간은 설정 가능한 한도로 제한한다. 무한 재시도, 자동 기대값 완화, 자동 skip·격리로 초록을 만들지 않는다. 수정 뒤에는 선택·검토·검증 지문을 다시 계산한다. 최종 전수 여부는 프로젝트 정책을 유지한다.

### 실행 순서와 실제 실행 경로

초기 단계에서 실행 순서를 최적화하더라도 필요한 테스트를 예산 때문에 버리지 않는다. 시간 기록과 최근 실패 이력으로 중요한 피드백을 먼저 얻는 방식을 검토하되, 최종 필요한 집합을 실행했는지 원장이 확인해야 한다.

향후 전수 실행에서 spec별 실행 소스를 수집해 정적 그래프와 대조할 수 있다. 이는 보조 증거다. Playwright Coverage API는 Chromium 계열에 한정되고, 번들·소스맵·동적 로딩·실행되지 않은 분기를 고려해야 한다. 현재 단계의 필수 범위에 넣지 않는다.

## 9. 섀도 신뢰도와 실패 주입 복구

현재 전수 성공도 hit로 계산된다. 실패가 없는 실행만 세 번 쌓였다고 해서 누락 탐지 능력을 실증한 것은 아니다. 서로 다른 변경 유형, 선택 비율, 실제 실패 포착, 오류·모바일 사례를 함께 보고 승격을 제안한다. 앱·프로젝트·모드별 신뢰도를 나눌 필요도 검토한다. 신뢰 승격은 계속 사람의 결정으로 둔다.

**현재 안내 오류:** `skills/shadow/SKILL.md` §6은 임시 브랜치에서 실패를 주입한 뒤 `git switch -`와 `git branch -D e2e-drill`로 복구하라고 한다. 별도 임시 Git 저장소에서 동일 절차를 재현했을 때 미커밋 실패가 원래 브랜치에 남았다. 브랜치 전환·삭제는 작업 트리 변경의 복구가 아니다. Codex 미러 `plugins/e2e-rail/skills/shadow/SKILL.md`에도 같은 안내가 있다.

우선 수정할 계약:

1. 실패 주입은 별도 작업 디렉터리에서 수행한다. 현재 미커밋 변경을 검증하려면 그 입력을 명시적으로 스냅샷으로 재현한다.
2. 원본 작업 트리와 index를 변경하거나, 사용자의 변경을 stash/reset/checkout으로 덮지 않는다.
3. 실험용 빌드·포트·원장을 분리한다. 실험 결과가 실제 last-green·섀도 신뢰도에 들어가지 않게 한다.
4. 성공·실패·중단 모두에서 정리하고, 종료 후 원본 상태가 실험 전과 같은지 확인한다.
5. 기대한 spec이 선택되고 실패하는 양성 대조와, 선택기가 놓치는 변경을 드러내는 음성 대조를 둔다. 단순히 spec에 실패 단언을 추가한 실험만으로 앱 변경의 영향 분석 능력을 증명하지 않는다.

## 10. 구현 순서 제안

| 단계 | 산출물 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 즉시 수정 후보 | 실패 주입 격리·복구 안내와 양쪽 스킬 미러 보정 | dirty 원본 보존, 중단 복구 테스트 |
| 설계 검증 | 두 런타임 지원표, 개인·프로젝트 실행기 선택, 자동화 정책 | 실제 지원과 가정을 분리한 설계 판정 |
| 첫 기능 버전 후보 | 통합 진입 스킬, 준비 상태 확인, 실행 계획·검토 기록, 중복 방지 | 일반 개발 요청만으로 정상·실패·재개 흐름 수행 |
| 효율 보강 | 미매핑 원인·비용 진단, 근거 관계 재사용, 제한된 실패 분석 | 실제 누락 없이 반복 조사·실행 비용 감소 |
| 후속 연구 | 실행 소스 매핑, 정밀 신뢰도·실행 순서 최적화 | 별도 측정으로 가치 확인 |

우선순위가 낮은 기능을 첫 버전에 한꺼번에 넣지 않는다. 다음 버전 번호는 구현 시 원격 최신 태그와 호환성 변경을 확인해 결정한다. 과거 대화의 예시 버전을 그대로 사용하지 않는다.

## 11. 필수 검증 시나리오

공통 CLI 테스트와 **실제 Claude·Codex 설치 상태에서의 평가**를 분리한다. 후자는 플러그인 명령을 프롬프트에 넣지 않고 실행한다.

| 시나리오 | 기대 결과 |
| --- | --- |
| “주문 검색 조건 수정해줘” | 구현 뒤 영향 분석·필요 실행·verify가 별도 지시 없이 수행됨 |
| “이 코드 설명해줘” | 불필요한 설정 변경·브라우저 실행 없음 |
| 이미 초기 설정된 프로젝트 | 동일한 설치·허용 질문 반복 없음 |
| 개인 플러그인 모드 | 프로젝트 package·lock·ignore를 임의로 수정하지 않음 |
| 아직 준비되지 않은 프로젝트 | 원인을 설명하고 필요한 초기 설정만 모아서 처리 |
| 동일 코드로 작업 재개 | 유효한 결과 재사용, 중복 실행·중복 큐 등록 없음 |
| 영향 검토 후 코드 변경 | 선택과 검토 기록 재평가, 이전 판단으로 새 코드를 통과시키지 않음 |
| 모달·URL·공용 fixture 변경 | 숨은 소비처가 근거와 함께 추가됨 |
| 문서 변경·전역 셸 변경 | 각각 불필요한 실행 회피·정책상 전수 실행 |
| 실패 후 단독 재실행 성공 | 원본 실패 유지, 전체 성공으로 보고하지 않음 |
| 훅 미신뢰·권한 거절·지원 이벤트 없음 | 미실행·미검증 상태 명확화, 조용한 성공 없음 |
| 세션 중단·축약·재개 | 미완료 실행과 무효 지문 복구, 훅 재귀·무한 재실행 없음 |
| 여러 워크트리의 동시 요청 | 상태 혼선 없음, 머신 락 준수, 검증 결과의 코드 일치 |
| 실패 주입 도중 종료 | 원본 파일·index 유지, 실험 원장 격리 |

평가 기록에는 런타임·모델·버전·권한·설치 모드·입력 요청·실제 호출·실행 종류·지문·사용자 개입 횟수를 남긴다. 한 번의 성공을 일반적인 자동 호출 보장으로 해석하지 않는다. 실행 환경이 없으면 해당 항목을 미검증으로 보고하고 단위 테스트로 대체 통과시키지 않는다.

성능 평가는 전체 작업 시간, 에이전트 판단 시간, 락 대기, 빌드, 테스트 실행, 재실행 횟수를 분리한다. 동일 코드·기계·모드·데이터 조건에서 비교한다. 목표는 사용자 개입과 중복 작업 감소이며, 정확성 저하를 속도 개선으로 보고하지 않는다.

## 12. 완료 기준과 산출물

- 사용자에게 일반 개발 요청만 받아도 초기 설정 이후 E2E 절차가 이어진다. 스킬명을 직접 호출해야만 성공하면 자동 운영 완료가 아니다.
- 두 런타임의 지원표와 평가 결과가 있고, 모델 안내에 의존하는 부분과 코드로 강제하는 부분이 구분돼 있다.
- 선택·검토·실행·검증이 같은 코드와 실행 조건을 가리킨다. 변경·중단·구버전 기록을 거짓 성공으로 인정하지 않는다.
- 필요한 전수 게이트, 섀도 상태, 머신 락을 유지한다. 개인 사용과 팀·CI 사용의 설치·상태 경계가 명확하다.
- 새 스킬·훅·CLI는 재진입 안전성과 실패 경로를 검증한다. 기존 단위·계약·버전 일치·미러 테스트도 통과한다.
- 통과 판정의 의미가 달라지면 `VERIFY_POLICY`와 기존 원장·섀도 상태의 이행을 검토한다. 스케줄링 변화만으로 불필요하게 정책을 올리지 않는다.
- 구현 보고는 채택·보류 결정, 변경 파일, 테스트 결과, 실제 자동 호출 평가, 남은 제한을 포함한다. 배포를 요청받았다면 버전·태그·두 플러그인·원본과 guardrail 설치 안내까지 맞춘다.

현재 보고서 작성 단계에서는 제품 코드·스킬을 수정하지 않았고, 새 에이전트를 실행하거나 메시지를 보내지 않았다.

## 13. 다음 모델에 전달할 요청

> 이 보고서를 읽고 e2e-rail의 현재 원격 코드와 대조해 독립 검토하라. 목표는 Claude Code와 Codex에 설치하고 프로젝트 초기 설정을 마친 뒤, 사용자가 스킬명을 지시하지 않아도 개발 요청에 필요한 E2E 절차가 이어지는 것이다. 먼저 실패 주입 복구 안내와 런타임별 자동 진입 가능성을 검증하고, 개인 플러그인 사용 시 프로젝트 의존성을 임의로 바꾸지 않는 실행기 구성을 결정하라. 채택할 최소 구현 범위와 근거를 정리한 뒤, 사용자에게 위임받은 범위에서 구현·테스트하라. CLI 단위 테스트와 실제 모델의 자동 호출 평가를 구분하고, 기존 검증·섀도·락 규칙을 약화하지 마라. 커밋·태그·푸시·사용자 환경 설치는 해당 세션의 사용자 지시에 따른다.
