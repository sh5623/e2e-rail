# spec 색인 — 스코프 해석과 손잡이 추적 (0.4.3 · 2026-11-03)

작성: Claude (구현) · 독립 검증: Codex (1차 · 2차 · 3차 · 4차 · 5차 재검증) · 브랜치 `feat/spec-index-loop-bindings` · 기준 `4f276d4`(v0.4.2)

## 왜

채택 저장소(bfm · spec 247)에서 22개가 `unmapped` 였고, 선택 실행마다 22개(직렬 약 600초)가 무조건 따라붙었다. 원인은 22/22 가
«정적으로 못 읽는 `goto` 인자»였다. 그중 17개는 데이터 주도 테스트(`for (const entry of [...]) test(…, () => page.goto(entry.url))`)라
spec 쪽에서 리터럴로 바꾸려면 테스트를 풀어 써야 했다. 나머지 5개(헬퍼 인자 · URL 조립 함수 호출)는 spec 쪽에서 고쳤다.

## 무엇을 읽게 됐나

`goto`/`route()` 인자를 **렉시컬 스코프**로 해석한다(종전: 최상위 `const` 와 import 한 단계만).

- `describe`·테스트 본문의 `const` · `for (const … of <배열 리터럴>)` 변수(구조 분해 포함 — 각 원소를 뜻한다) · 숫자 인덱스 · `+` ·
  `?:`/`??`/`||` 의 양쪽 합집합. 한 인자는 최대 64개 값.
- 계속 읽지 않는 것: 매개변수 · `let`/`var`(함수 안 `var` 호이스팅 포함) · catch · 호출 결과 · 스프레드 · 구조 분해 기본값 · import 두 단계.

## 손잡이 추적 — 좁힘 안전성 (1차 검증 F1~F3 반영)

리터럴 배열·객체는 **이름(손잡이)을 통해** 읽으므로, 실행 중 그 내용이 바뀔 수 있으면 읽은 값이 실제 방문 경로와 달라진다
(선택에서 조용히 빠짐). 그래서 리터럴을 가진 이름의 **모든 참조**(스코프로 같은 선언에 묶이는 것만)를 따라간다.

| 참조가 닿는 자리 | 처리 |
| --- | --- |
| 원시값 읽기(문자열 멤버 · 비교 · 템플릿 · 인덱스로 쓰임) | 끝 — 원시값은 손잡이로 바뀌지 않는다 |
| 정적 멤버·인덱스 접근 | 그 값으로 한 단계 내려가 계속 |
| `const` 별칭 · for-of 변수(반복자를 돌리므로 내재 객체 층이 온전할 때만 — 배열 패턴도 같다) · e2e 트리에 선언된 헬퍼(같은 모듈 또는 import 한 단계)의 매개변수 | 그 이름의 참조를 이어서 따라감(헬퍼 4단계까지). 헬퍼는 **이름이 한 번도 재할당되지 않고**(함수 선언은 재할당될 수 있다 · 2차 G3) 그 모듈이 통째로 노출되지 않을 때만 따라간다. `arguments` 를 쓰는 함수는 오염 |
| `some`·`every`·`find`·`findLast`·`findIndex`·`findLastIndex`·`forEach` 의 콜백(인라인 또는 위 헬퍼) | 콜백 첫 매개변수로 원소를 따라감. `find` 결과는 원소 손잡이로 계속. 셋째 매개변수(배열 자체)·나머지 매개변수는 오염 |
| 배열 리터럴의 내장 읽기 전용 메서드(`includes`·`indexOf`·`lastIndexOf`·`join`·`toString`) · `expect(…)`(Playwright)와 그 매처 · `JSON.stringify`(인자 1개)·`console.*`·`Object.keys` · `===`/`!==`/`in` | 끝 — 읽기만 한다. 단 아래 «내장 무결성»의 해당 층(배열 메서드는 내재 객체, `JSON`·`console`·`Object` 는 그 전역, `expect` 는 expect 층)이 온전할 때만 |
| 형변환(템플릿 · `+` · `==` · `<` · 단항 `+`/`-`) | 순수 데이터면 내장 `toString`/`valueOf` 만 돈다 → 끝. 내재 객체 층이 깨졌으면 오염 |
| 그 밖의 모든 곳: 쓰기 · 삭제 · `++` · 다른 호출의 인자(`Object.assign`·`defineProperty`·`Reflect.set` 포함) · 반환 · `let`/`var` 별칭 · 다른 리터럴에 담기 · 다른 메서드 · 스프레드 복사 · 태그드 템플릿 · `instanceof` | **오염** — 그 리터럴과 안의 모든 리터럴을 읽지 않는다 |

**순수 데이터만 읽는다**(1차 F3 · 2차 G2): 메서드·접근자·함수/클래스 값·계산된 키·스프레드·`__proto__`·런타임이 스스로 부르는 키
(`toString`·`toLocaleString`·`valueOf`·`toJSON`·`then`·`constructor`)가 있는 객체 리터럴은 키와 무관하게 읽지 않는다 — 읽기·호출·
형변환이 사용자 코드를 돌려 어떤 키든 바꿀 수 있다. 메서드 «이름»은 내장임을 보증하지 않는다.

**분석 트리 = 한 워커가 싣는 모듈 전부**(2차 G1 · 3차 L2): Playwright 는 한 워커 프로세스에서 여러 spec 파일을 돌리고 support 모듈
인스턴스를 공유한다. 그래서 export 된 상수의 별칭·변이 검사와 아래 «내장 무결성» 은 spec·support 디렉터리, Playwright 설정, 그리고
그것들이 실행 시점에 import 하는(타입 전용 제외) **모든 프로젝트 파일**을 이행적으로 모은 트리에서 한 번 판정한다(색인 순서와 무관).
디렉터리 밖 파일(`src/fixtures/…` 등)은 색인 캐시에 `treeExtra` 로 기록되고 캐시 키에 내용이 들어간다 — 트리는 이미 키에 든 파일을
고쳐야만 바뀌므로 이 기록으로 충분하다. 통째로 가져가는 import(namespace·default·`require`·`import()`·재-export)가 트리 어디에 있든 그
모듈의 export 는 읽지도, 그 모듈의 헬퍼를 따라가지도 않는다.

**내장 무결성 — 금지 목록이 아니라 허용 목록**(3차): 반복문·배열 패턴은 배열 반복자를, 배열 메서드·형변환은 내장을 돌린다. 2차까지는
«내장을 바꾸는 알려진 형태»를 찾아 막았고, 3차에서 같은 부류의 우회가 검증자 6건(문자열 인덱스 `Array['prototype']`, 이름이
`evaluate` 인 Node 헬퍼)·구현자 10건(반복자 교체 뒤 for-of, `__defineGetter__`, `Reflect.get([], '__proto__')`, 조립 문자열 키,
`vm`, …)이 나왔다. 특히 반복자 교체는 «변경은 감지하는데 for-of 가 그 판정을 보지 않는» 논리 결함이었다. 그래서 판정을 뒤집었다:
트리의 모든 모듈이 아래 허용 형태 안에 있을 때만 믿는다. 신뢰는 세 층이다.

| 층 | 이것이 믿게 하는 것 | 깨는 것(트리 어디든 하나라도) |
| --- | --- | --- |
| 내재 객체 | for-of·배열 패턴(반복자), 배열 읽기 전용 메서드·콜백 메서드, 형변환 — 아래 두 층의 전제 | 위험 이름(`prototype`·`__proto__`·`constructor`·`getPrototypeOf`·`getOwnPropertyDescriptor(s)`·`__lookupGetter__`/`__lookupSetter__`·`eval`·`Function`)이 식별자·속성명·문자열·색인이 풀 수 있는 문자열식(`'__pro' + 'to__'`·템플릿·const) 어디에든 · 풀 수 없는 키로 전역 내장 읽기(`Object[k]`) · 풀 수 없는 키 너머 쓰기(`x[k].y = v`, `const p = x[k]; p.y = v`, `Reflect.get` 도 같다) · 전역 객체·`Error`·선언 없는 이름에 쓰기 · `Object`·`Array`·`Function`·`Reflect`·`Iterator`·전역 객체·`require` 넘기기 · 느슨한 모드 파일의 클래스 밖 `this` · `with` 문(4차 H4 — 그 객체가 브라우저 전용 이름까지 무엇이든 대신한다 · 그 모듈은 읽지도 않는다) · `vm`/`module`/`inspector`/`repl`·`data:`/`http:` 모듈, 계산된 `require`/`import()` · `process.binding` 류와 `process.getBuiltinModule`(4차 H3) |
| 전역 내장 하나(`String`·`JSON`·`console`·`Object` …) | `String(x)`·`JSON.stringify(x)`(인자 1개)·`console.*(x)`·`Object.keys(x)`·`hasOwnProperty.call` | 내재 객체 층 + 그 전역에 쓰기(`Object.assign`·`__defineGetter__` 포함) · 그 전역을 넘기기(`.map(Number)`) |
| Playwright `expect` | `expect(x)` 와 매처 | 내재 객체 층 + 어떤 전역 내장이든 바뀜(매처는 아무 전역이나 부르는 라이브러리 코드다) + `expect` 확장·쓰기·개명·넘기기 |

브라우저 전용 전역(`window`·`document`·`location`·`history`·`Element`·`Document`·`HTML…Element`·`SVG…Element`)에 뿌리를 둔 사슬은
예외다. 그 전역은 Node 테스트 프로세스에 없으므로(Node 26 실측: `navigator`·`sessionStorage` 는 있어서 목록에 넣지 않았다) 그 식은
Node 에서 던지고 끝나 내장을 바꿀 수 없다. 2차의 «`addInitScript`·`evaluate` 의 함수 인자 제외»는 호출 **이름**만 보고 Node 헬퍼를
빼는 결함(3차 H2)이라 걷었고, 페이지 함수도 다른 코드와 똑같이 이 규칙으로 판정한다. 그 이름을 Node 에 만들어 예외를 뚫는 길
(느슨한 코드의 `HTMLFormElement = …`, 전역 객체 쓰기)은 내재 객체 층이 막는다. 예외 하나 더: `Object.prototype.hasOwnProperty.call(…)`·
`….propertyIsEnumerable.call(…)` 의 `prototype` 은 정확히 그 형태일 때만 허용한다.

`map --check` 는 층마다 처음 깨는 위치를 출력한다(`builtins: intact` 또는 `changed — <파일:줄> <이유>`, `global changed: …`,
`expect changed: …`). 데이터 주도 spec 이 갑자기 미매핑이 되면 그 줄이 이유다.

추가로 읽지 않는 것: `eval`/`Function` 을 부르는 모듈, `with` 문이 있는 모듈(4차 H4 — 안의 이름이 선언이 아니라 객체 속성일 수 있다).

남는 한계(설계상 경계 · 문서화):
- 실행 중에만 생기는 위험 이름 — 메서드 호출로 조립하거나(`['__pro','to__'].join('')`), 데이터·반영(`Object.getOwnPropertyNames`)에서
  읽은 문자열이 **호출·반환·매개변수를 거쳐** 키가 되는 경우. 한 단계(직접 쓰기·const 별칭 쓰기·전역 내장 위)는 위 규칙이 막는다.
- 앱 루트 밖 코드(의존성·워크스페이스 패키지·`NODE_OPTIONS=--require`)가 내장을 바꾸는 경우 — 표준 동작을 가정한다.
- 색인 캐시 키(`INDEX_VERSION` · spec·support·폐포 파일 내용 · tsconfig)는 **도구 소스를 포함하지 않는다** — 개발 중 해석기를
  바꿨으면 `.e2e-rail/map.<app>.json` 을 지우고 다시 재야 한다(릴리스는 `INDEX_VERSION` 을 올려 해결 · 이 브랜치 6 — 4차 규칙 변경 때 올리지 않으면 3차 코드의 캐시가 그대로 쓰인다).
