# e2e-rail 0.4.0 Codex 교차검증

검증일: 2026-10-14 KST · 검토: Codex

대상: `8b5310f86dfb55cd11798608326409ccc198d48f`. 로컬 HEAD·원격 main·annotated `v0.4.0` tag의 대상 커밋이 일치한다. 소스 작업 트리는 검토 시작 시 clean이었다. 별도 임시 clone에서 의존성 설치·테스트·추가 재현을 수행했다.

## 판정

**측정과 동일 실행 합류로 범위를 축소한 방향은 타당하다. 다만 다른 실행 환경의 요청이 성공 결과에 합류하는 P1 결함을 재현했으므로, 0.4.0 합류 기능은 수정 후 재검증이 필요하다.**

이 버전은 최초 보고서의 단계 0과 1A 일부를 구현했다. 통합 후보 고정·Git 쓰기 조정·커밋 간 증거 재사용·테스트별 통합 증거는 구현하지 않았다. 따라서 동료 변경으로 코드가 달라진 에픽의 재게이트 비용을 직접 해결하는 릴리스로 설명하면 안 된다.

## P1 실행 환경이 다른 요청의 성공 결과 합류

위치: `src/run.mjs:295`의 `requestKey`, `src/run.mjs:417`의 request 생성과 합류 반환. 실제 자식 실행은 `src/util/exec.mjs`에서 `process.env`를 상속한다.

키는 코드 지문·앱·mode·목록·selection·shard·project·workers·blob·passthrough를 비교하지만 실행 프로세스의 환경을 비교하지 않는다. 두 세션이 같은 코드에서 서로 다른 대상 서버·계정·기능 플래그를 지정하면 두 번째 요청이 첫 번째 결과를 받는다. 파일 내용이 같다는 사실은 환경에 따라 계산된 설정값까지 동일하다는 증명이 아니다.

실제 `@playwright/test` 러너를 사용한 재현은 다음과 같다. 브라우저 fixture를 사용하지 않는 환경 계약 테스트이며, BFM이나 외부 서비스에는 접속하지 않았다.

1. 같은 clean Git tree에 `expect(process.env.PROBE_TARGET).toBe('healthy')` 테스트를 둔다. 외부 임시 marker로 첫 실행을 잠시 대기시킨다.
2. producer는 `PROBE_TARGET=healthy`, follower는 `PROBE_TARGET=broken`으로 각각 별도 프로세스에서 동일한 `run --app web --full --workers 1`을 실행한다.
3. follower가 머신 heavy 락에 대기한 것을 확인한 뒤 producer를 완료시킨다.
4. 비교 대조군으로 `broken` 요청을 다시 단독 실행한다.

| 관측 | 결과 |
| --- | --- |
| producer healthy | rc 0 |
| 동시 follower broken | **rc 0, `reused: run ...` 출력, 해당 테스트 실행 없음** |
| 단독 broken 대조군 | **rc 1**, 환경 단언 실패 |
| 실제 테스트 호출 | healthy 1회, 단독 대조군 broken 1회. 합류한 broken 요청은 실행되지 않음 |
| 원장 코드 상태 | 두 실제 실행 모두 `fingerprint.clean: true` |

`broken` 환경에서 이어서 실행한 verify도 다음을 출력했다.

```text
verified: full@run-20261013-234105-f945 (just now)
```

이는 정상 통과의 증거가 아니라 **기존 verify 역시 환경을 구분하지 못해 잘못된 합류를 방어하지 못한다는 관측**이다. 기존 verify의 환경 한계와, 0.4.0이 명시적으로 요청한 실행을 자동 생략하는 새 동작은 구분해야 한다. 대기 창이 짧다는 이유로 두 프로세스의 환경이 같아지지는 않는다.

수정 방향:

- 합류의 실행 동등성 계약에 실제 적용되는 설정·상속 환경을 포함한다. 프로세스·브라우저 런타임 차이도 어떤 범위까지 지원할지 명시한다.
- 동등성을 입증할 수 없으면 합류하지 않고 원래 요청을 실행한다. 통제된 실행 환경에서만 opt-in하는 보수적인 방식도 가능하다.
- 원장에 비밀 환경값을 평문으로 남기지 않는다. 비교용 digest를 도입하더라도 입력 정의·비밀정보 처리·혼합 버전의 호환성을 함께 결정한다.
- 동등성 정보가 없는 0.4.0 원본 실행은 새 합류 판정에 사용하지 않는다. 기존 `VERIFY_POLICY`와 합류 계약 버전을 어떻게 나눌지 명시한다.
- 회귀 테스트는 동일 환경 합류 성공, 다른 환경 합류 거부, 설정에서 환경을 읽어 `run.env`를 계산하는 경우, 구형 원장 거부를 포함한다.

Claude 판정 문서 Q3의 «기존 verify와 같은 한계이고 창이 좁다»는 보류 근거는 이 재현으로 재검토해야 한다. 원본 검토 문서는 수정하지 않았다.

로컬 실행 환경은 Node `v26.3.0`, lockfile로 설치한 Playwright `1.63.0`이다. Node 20·22와 Playwright 1.56의 결과는 로컬 실행이 아닌 GitHub CI 조회 결과다. 추가 환경 재현은 기존 360/5 테스트 밖의 검증이다.

원장 기록 전에 락을 해제하던 순서를 고친 점, 새 실행을 위조하지 않고 원본 run ID를 반환하는 점, 정책 2와 기존 full/shard/selected 의미를 유지한 점은 타당하다. 다만 통과한 기존 스위트가 환경 구분 결함을 포함하지 않았다는 사실은 위 P1과 별개다.

## 최초 개선 보고서와 Claude 판정의 대조

- **채택:** 별도 실행 레지스트리 대신 기존 락과 append-only 원장을 이용하는 간소화는 구현 규모를 줄인다. 정확히 같은 요청임을 보장하는 조건은 축소할 수 없다.
- **채택:** 현재 원장에 같은 tree의 다른 HEAD 재실행 수요가 없다는 관측을 근거로 단계 2를 당장 구현하지 않는 것은 합리적이다. 해당 BFM 원장 집계는 Claude가 기록한 결과이며 이번 검토에서 다시 측정하지 않았다.
- **구분 필요:** 기존 `select --base <검증 head>`는 변경 영향 선택이다. 두 부모 실행의 증거를 합치는 통합 증거 재사용과 동일하지 않다. 단계 3 전체가 이미 구현됐다는 의미로 읽으면 안 된다.
- **구분 필요:** 머신 FIFO는 E2E 프로세스의 입장 순서를 정한다. 후보 내용 고정·에픽 변경 묶음·Git 쓰기 소유권은 제공하지 않는다. 1B는 여전히 프로젝트 운영 영역이다.
- **효과 제한:** 합류는 같은 원장을 보고 e2e-rail 락을 쓰는 중첩 요청에 적용된다. 다른 worktree 원장, `--no-lock`, 변경된 HEAD의 통합 재검증에는 직접 적용되지 않는다. 원래 사용자의 에픽 병목에는 프로젝트 재게이트 정책과 유닛/build 비용 분석이 남는다.
- **측정 제한:** `measure time`은 원장에 남은 실행을 보여준다. preview build 실패는 기존처럼 entry 없이 반환되고 follower 대기 결과도 원장에 추가되지 않아, 전체 요청의 실패·대기 비용을 모두 계측한 것은 아니다.
